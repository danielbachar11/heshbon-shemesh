# סנכרון אוטומטי של עסקאות ישראכרט

## 1. מה מצאתי במערכת הקיימת
- **היכן נשמרות הוצאות:** טבלת התנועות היחידה (הכנסות + הוצאות), סכום חיובי תמיד, סוג = הכנסה/הוצאה.
- **שיוך:** כל תנועה שייכת למשתמש שיצר אותה ולמשק בית (נקבע אוטומטית בשרת לפי המשתמש). כל חברי משק הבית רואים ועורכים אותה.
- **קטגוריות:** קטגוריה ראשית חובה במסד (ברירת מחדל "הוצאות אחרות"), תת-קטגוריה אופציונלית.
- **כפילויות:** אין כרגע שום מנגנון.
- **מקור / מזהה חיצוני / כרטיס אשראי:** לא קיימים.
- **תשלומים:** לא נשמרים (יש רק "קבוע/חד-פעמי").
- **חישוב סיכומים:** במסך, סכום התנועות לפי תאריך התנועה בחודש הנבחר. אין תקציבים שמורים.
- **מסך הגדרות:** לא קיים — ייבנה חדש.

נשתמש באותה טבלת תנועות — בלי מערכת מקבילה. עסקאות מיובאות יופיעו בסיכומים כמו כל הוצאה.

## 2. שינויים במסד הנתונים (תוספות בלבד, בלי לגעת בנתונים קיימים)

**עמודות חדשות בטבלת התנועות (כולן ריקות כברירת מחדל):**
source (manual/isracard), external_account, external_id, import_key, charged_date, original_amount, original_currency, charged_amount, installment_number, installments_total, external_status (pending/completed), user_modified (האם המשתמש ערך ידנית), needs_review, review_reason, linked_transaction_id.

**אינדקס ייחודי:** (household_id, source, external_account, import_key) כאשר import_key קיים — מבטיח ברמת המסד שאין כפילות גם בבקשות מקבילות.

**טבלאות חדשות:**
- `sync_api_keys` — משק בית, שם, hash (SHA-256) של המפתח, 8 תווים ראשונים לזיהוי, נוצר/בוטל/שימוש אחרון. המפתח הגלוי מוצג פעם אחת בלבד.
- `sync_logs` — זמן, מקור, התקבלו / חדשות / קיימות / עודכנו / לבדיקה / שגיאות, פירוט שגיאות.
- הרשאות: חברי משק הבית רואים רק את שלהם; כתיבה ל-hash ולוגים רק מצד השרת.

**טריגר:** עריכה ידנית של קטגוריה / הערות / תיאור / בן משפחה מסמנת user_modified = true.

## 3. אסטרטגיית מניעת כפילויות

### 3.1 מה הספרייה מחזירה (ישראכרט)
- `identifier` — מספר שובר. לרוב קיים בעסקאות סופיות. אותו מספר חוזר בכל תשלומי אותה רכישה. בעסקאות ממתינות הוא לפעמים חסר.
- `type`: `normal` או `installments`; `installments: { number, total }`.
- `status`: `pending` או `completed`.
- `date` = תאריך הרכישה, `processedDate` = תאריך החיוב.
- `originalAmount` = סכום הרכישה המלא; `chargedAmount` = מה שחויב בפועל החודש (בתשלומים: התשלום החודשי).
- אין שעת עסקה ואין מזהה ייחודי נוסף.
- **לפני הפיתוח:** אריץ את הסקריפט שלך עם פלט לדוגמה (או תשלח לי פלט אמיתי מוסתר) כדי לוודא שהשדות האלה באמת מגיעים כך.

### 3.2 שני סוגי מפתחות
1. **מפתח חזק** (כשיש `identifier`): `<accountNumber>|<identifier>|<installment.number או 0>`.
   יציב בין סנכרונים, לא תלוי בסדר או בכמות העסקאות בבקשה.
2. **טביעת אצבע** (כשאין `identifier`): SHA-256 של חשבון + `date` + `originalAmount` + מטבע + `description` מנורמל + מספר תשלום וסה"כ.
   **בלי מספר מופע.** טביעת אצבע לא נחשבת ייחודית, ולכן היא עוברת את תהליך ההתאמה בסעיף 3.3.

אינדקס ייחודי ברמת המסד רק על המפתח החזק: (משק בית, מקור, חשבון, מפתח).

### 3.3 התאמה כשאין מזהה מקורי (ספירה מול המסד)
לכל טביעת אצבע: N = כמה פעמים היא מופיעה בבקשה הנוכחית, M = כמה עסקאות מיובאות כבר קיימות איתה (כולל אלה שבבדיקה).
- **N ≤ M** — כולן כבר קיימות. לא נוצר כלום.
- **M = 0 ו-N = 1** — נקלטת כהוצאה רגילה.
- **N > 1, או N > M כש-M > 0** — יש ספק. העסקאות העודפות (N−M) **נשמרות ברשימת "ממתין לבדיקה" ולא נספרות בהוצאות**, עד שתאשר.

### 3.4 שתי עסקאות אמיתיות עם אותו תאריך, סכום ותיאור, בלי מזהה
- סנכרון ראשון: N=2, M=0 → שתיהן נכנסות ל"בדיקה" עם הסבר "2 עסקאות זהות". לא נוספות להוצאות.
- תאשר "שתיהן אמיתיות" → שתיהן הופכות להוצאות. המערכת זוכרת שיש 2 עם טביעת האצבע הזו.
- סנכרון למחרת: N=2, M=2 → לא נוצר כלום.
- אם בעתיד מגיעה גם שלישית (N=3, M=2) → רק אחת עוברת לבדיקה.
- תסמן "זו כפילות" → נשמרת אחת. השנייה נשמרת כ"נדחתה" (לא נספרת), כדי שלא תחזור שוב לבדיקה.
- אם ישראכרט מחזירה פחות עסקאות מבעבר (N < M), **לא מוחקים כלום**.

### 3.5 הגנה מסנכרון חוזר ומבקשות מקבילות
- כל הקליטה רצה בפעולה אחת במסד, עם נעילה לפי משק בית ומקור. שתי בקשות מקבילות לא רצות יחד על אותו משק בית — השנייה ממתינה ואז רואה את מה שהראשונה הכניסה.
- מפתחות חזקים: `ON CONFLICT` — אי אפשר ליצור כפילות גם אם הנעילה נכשלת.
- תקשורת נכשלה באמצע? שליחה חוזרת של אותה בקשה תמיד בטוחה: הכל או כלום.

### 3.6 ממתינה → סופית
- ממתינה נשמרת עם status=pending. היא נספרת בהוצאות כמו היום.
- כשמגיעה עסקה סופית: קודם מחפשים לפי המפתח החזק. אם לא נמצאה, מחפשים ממתינה באותו חשבון, אותו `originalAmount`, תיאור דומה ותאריך ±5 ימים.
  - **התאמה יחידה** → הממתינה **מתעדכנת** לסופית ומקבלת את המזהה. לא נוצרת הוצאה שנייה.
  - **כמה התאמות** → הסופית נכנסת לבדיקה (לא נספרת) עם קישור למועמדות.
- ממתינה שלא הופיעה 14 יום ולא הפכה לסופית → מסומנת לבדיקה (לא נמחקת).

### 3.7 תשלומים — בלי ספירה כפולה
- הספרייה מחזירה שורה לכל חודש חיוב, לא שורה לרכישה המלאה. נשמר **רק `chargedAmount`** של החודש, בתאריך החיוב. `originalAmount` נשמר לתצוגה בלבד ("3 מתוך 12, סה"כ ₪1,200") ולא נכנס לסכומים.
- כל תשלום מקבל מפתח משלו לפי מספר התשלום, כך שתשלום 3 לא דורס את תשלום 2.
- אם תשלום מגיע בלי `installments.number` → לבדיקה.

### 3.8 התאמה להוצאות שהזנת ידנית
- לכל עסקה מיובאת חדשה מחפשים הוצאה ידנית לא מקושרת באותו סכום (`chargedAmount`, או `originalAmount` לרכישות רגילות), תאריך ±3 ימים.
- נמצאה → העסקה המיובאת **לא נוספת כהוצאה**. היא נכנסת לבדיקה כ"ייתכן שכבר הוזן ידנית" עם ההוצאה המוצעת.
- **"קשר"** → ההוצאה הידנית נשארת כמו שהיא (קטגוריה, תיאור, הערות, בן משפחה). היא מקבלת את מזהה המקור, ומעכשיו הסנכרונים מזהים אותה. לא נמחק כלום.
- **"לא קשורות"** → המיובאת נוספת כהוצאה נפרדת, וההחלטה נזכרת.

### 3.9 שמירת שינויים ידניים
- טריגר מסמן אילו שדות שינית: קטגוריה, תת-קטגוריה, תיאור, הערות, בן משפחה.
- הסנכרון מעדכן רק סכום חיוב, תאריך חיוב וסטטוס, ולעולם לא נוגע בשדות שסומנו.
- סכום שהשתנה בעסקה שכבר קושרה → מתעדכן ומופיע בהיסטוריית הסנכרון.

### 3.10 זיכויים
סכום חיובי בפלט (החזר) → נשמר כהכנסה בקטגוריה "זיכוי", באותו מנגנון.

## 4. מבנה בקשת ה-JSON
```text
POST .../functions/v1/sync-transactions
Header: x-api-key: <המפתח>

{
  "source": "isracard",                       // חובה
  "accounts": [
    {
      "accountNumber": "1234",                // חובה — חלק מכל מפתח
      "txns": [
        {
          "identifier": 98765,                // מזהה מקורי, מפתח חזק (אם קיים)
          "type": "installments",             // normal / installments
          "status": "completed",              // pending / completed
          "date": "2026-10-20T00:00:00.000Z", // תאריך רכישה — מזהה
          "processedDate": "2026-11-02T00:00:00.000Z", // תאריך חיוב
          "originalAmount": -1200,            // מזהה, לא נספר בסכומים
          "originalCurrency": "ILS",          // מזהה
          "chargedAmount": -100,              // הסכום שנספר
          "chargedCurrency": "ILS",
          "description": "שופרסל",            // מזהה (מנורמל)
          "memo": "",
          "installments": { "number": 3, "total": 12 } // מזהה
        },
        {
          "status": "pending",                // ממתינה בלי מזהה → טביעת אצבע
          "type": "normal",
          "date": "2026-10-21T00:00:00.000Z",
          "originalAmount": -45.9,
          "originalCurrency": "ILS",
          "chargedAmount": -45.9,
          "description": "קפה ג'ו"
        }
      ]
    }
  ]
}
```
זה המבנה ש-`scrapeResult.accounts` מחזיר — הסקריפט שולח אותו כמו שהוא. אין household_id בבקשה. מספר הכרטיס נשמר רק ב-4 ספרות אחרונות.

**תשובה:**
```text
{ "ok": true, "sync_id": "...", "received": 40, "inserted": 3, "existing": 34,
  "updated": 1, "pending_to_completed": 1, "needs_review": 1, "errors": 0,
  "failed": [ { "accountNumber": "1234", "identifier": 98765, "reason": "invalid date" } ] }
```
אם יש שגיאה כללית, הבקשה כולה מתבטלת ומוחזרת שגיאה. אפשר לשלוח את אותה בקשה שוב.

## 5. הפונקציה בשרת (sync-transactions)
- מאמתת את המפתח לפי hash, ומזהה את משק הבית רק משם. בלי צורך בהתחברות משתמש.
- הגבלת גודל: עד 1MB ועד 2,000 עסקאות לבקשה; בדיקת תקינות לכל שדה.
- הגבלת קצב פשוטה: עד 30 בקשות לשעה למפתח (לפי טבלת הלוגים). אין במערכת מנגנון מובנה לכך, זו הגבלה בסיסית.
- הלוגים לא שומרים מפתחות, מספרי כרטיס מלאים או סכומים — רק ספירות.
- ההוצאות נרשמות על שם בעל המפתח (מי שיצר אותו). הסקריפט לא מקבל שום מפתח ניהול.

## 6. ממשק — דף "הגדרות" חדש ← "סנכרון עסקאות אשראי"
- מצב חיבור (פעיל / לא פעיל), סנכרון אחרון, כמה נקלטו בו.
- יצירת מפתח (מוצג פעם אחת עם כפתור העתקה), ביטול, החלפה.
- היסטוריית סנכרונים (טבלה).
- עסקאות לבדיקה: אישור / מיזוג עם הידנית / מחיקה.
- דוגמת קוד מוכנה לסקריפט במחשב שלך.
- כניסה לדף מכפתור הגדרות בדשבורד. ברשימת התנועות — סימן קטן "ישראכרט" לעסקאות מיובאות.

## 7. בדיקות
בדיקות אוטומטיות לחישוב מפתח הייבוא, ובדיקות מול הפונקציה האמיתית:
אותן עסקאות פעמיים; שתי בקשות במקביל; שתי עסקאות זהות; עסקה ששונתה; תשלומים; מפתח שגוי (401); מפתח של משק בית אחר לא רואה/נוגע בנתונים; התאמה להוצאה ידנית. בסיום — מחיקת נתוני הבדיקה.

## 8. מה לא משתנה
אין מחיקה או שינוי של הוצאות קיימות. סיכומים, גרפים וייצוא לאקסל ממשיכים לעבוד; העסקאות המיובאות פשוט מצטרפות אליהם (למעט אלה שבבדיקה).
